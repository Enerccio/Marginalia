# データベースのバックアップ

データベースのバックアップは、Marginaliaのデータベース全体の完全なコピーです。すべてのユーザーとその作品、ロアブック、設定、拡張機能のデータがすべて含まれます。インストール環境をミスや障害から守るため、また別のコンピューターへ移すために使います。単一の作品をバックアップする場合は、ユーザー向けの[作品のバックアップ](../books/backups.md)を使ってください。

![データベースのバックアップタブ](../../images/admin-database-backups.png)

<a id="creating-a-backup"></a>

## バックアップの作成

**データベースのバックアップ**タブで**バックアップを作成**をクリックします。コピーはMarginaliaの実行中に作成され、人が執筆している最中でも整合性が保たれます。一覧には**名前**、**作成日時**、**種類**（*手動*または*定期*）、**サイズ**が表示されます。ツールバーにはデータベースの現在のサイズが表示されます。

各バックアップには次のボタンがあります。

| ボタン | |
|---|---|
| **ダウンロード** | バックアップファイル（`.sqlite`）をダウンロードします。サーバーの外にもコピーを保管してください。 |
| **再起動時に復元** | バックアップを復元します。[下記](#restoring)を参照してください。 |
| ゴミ箱 | バックアップを削除します。 |

**バックアップをアップロード**では、バックアップファイル（`.sqlite`または`.db`）を一覧に追加できます。たとえば別のインストール環境からダウンロードしたファイルなどです。ファイルは最初に検査されます。SQLiteデータベースではない、破損している、Marginaliaのデータベースではない（別のアプリケーションのデータベース）、または実行中のものより新しいMarginaliaのバージョンで作成された場合は、理由とともに *The database can't be restored: ...* と表示されて拒否されます。

!!!warning バックアップには機密情報が含まれます
データベースのバックアップには、すべてのユーザーのパスワードのハッシュとAPIキーを含め、すべてが含まれます。APIキーは[データフォルダー](index.md#the-data-folder)内の`secret.key`ファイルで暗号化されています。このファイルはバックアップには含まれませんが、バックアップと`secret.key`の両方を持つ人は、APIキーを読み取れてしまいます。ダウンロードしたバックアップは、サーバー本体と同じくらい厳重に保管してください。
!!!

ファイルは[データフォルダー](index.md#the-data-folder)内の`db-backups`フォルダーに保存されます。Marginalia自身が作成するコピー、つまり[復元](#restoring)の前に作られる`pre-restore-...`と、[アップグレード](#copy-before-an-upgrade)の前に作られる`pre-migration-...`も一覧に含まれ、*手動*として表示されます。そのため、定期バックアップの世代管理によって削除されることはありません。作品のバックアップと拡張機能のJARは別ファイルであり、データベースのバックアップには含まれません。

**アップロードされたファイル（[パートの画像](../books/story-editor.md#images)）も、データベースのバックアップには含まれません。** データベースが知っているのは[リソース](../resources.md)タブのエントリーだけで、ファイル本体はデータフォルダーの`data/<login>/images`フォルダーにあります。それで問題ありません。復元後も、エントリーはバックアップ時点のものになり、それらが使用する画像はフォルダーに残っています。バックアップ後に追加された画像のファイルは、参照されなくなった残りファイルとしてディスク容量を消費します。画像を確実に保管するには、独自のバックアップにデータフォルダー全体を含めるか、[作品のバックアップ](../books/backups.md#pictures-in-a-backup)に画像をまとめてください。

別の**インストール環境**でバックアップを復元する場合は、元のインストール環境から`secret.key`もあわせてコピーしてください（Marginaliaを停止した状態で行います）。そうしないと、保存されたAPIキーを復号できず、すべてのユーザーが再度入力し直す必要があります。

<a id="scheduled-backups"></a>

## 定期バックアップ

**定期バックアップ**セクションでは、バックアップを自動で作成できます。

| 項目 | |
|---|---|
| **バックアップを自動作成する** | 定期バックアップをオンにします。 |
| **スケジュール（cron）** | バックアップを作成するタイミングを指定します。[下記](#schedule-syntax)を参照してください。次の3回の実行時刻が項目の下に表示されます。 |
| **定期バックアップの保持数** | 保持する定期バックアップの数です。古いものから削除されます。`0`にするとすべて保持します。手動バックアップとアップロードしたバックアップは削除されません。 |

適用するには**スケジュールを保存**をクリックします。ステータス行には、最後に定期バックアップが作成された時刻と、次回の予定時刻が表示されます。

予定時刻にMarginaliaが実行されていなかった場合（執筆中だけ起動するデスクトップアプリでは一般的です）、次回の起動から約30秒後に、取りこぼしたバックアップを作成します。

<a id="schedule-syntax"></a>

### スケジュールの書式

スケジュールは、5つのフィールドからなるcron式で、`分 時 日 月 曜日`の順に指定します。

| 式 | 実行タイミング |
|---|---|
| `0 3 * * *` | 毎日3:00 |
| `0 */6 * * *` | 6時間ごと |
| `30 2 * * 1` | 毎週月曜日の2:30（曜日は`0`または`7`が日曜日、`1`が月曜日…） |
| `0 12 1 * *` | 毎月1日の正午 |
| `@daily`、`@weekly`、`@monthly` | 毎日・毎週・毎月、深夜0時に1回（`@hourly`、`@yearly`も使えます） |

時刻はサーバーのタイムゾーンで解釈されます（Dockerでは`TZ`環境変数で設定します）。

!!!
定期バックアップをオフにするには、*バックアップを自動作成する*のチェックを外し、*スケジュールを保存*をクリックします。式は保持されるため、後で再びオンにできます。式は引き続き検査され、無効な式が保存されることはありません。ただし、バックアップがオフの間は、欄が空になっている場合もあります。
!!!

<a id="restoring"></a>

## 復元

Marginaliaが使用中のデータベースは置き換えられないため、復元は**次回の起動時**に行われます。

1. バックアップの横にある**再起動時に復元**をクリックし、確認します。
   タブに *Database restore is scheduled. Restart the application to apply it.* と表示されます。**復元を取り消す**で取り消せます。
2. Marginaliaを再起動します。[デスクトップアプリ](../getting-started/desktop-app.md)なら終了して起動し直し、[サーバー](../getting-started/docker-server.md)なら`docker compose restart`を実行します。

起動時に、現在のデータベースは`db-backups/pre-restore-<time>-marginalia.sqlite`に移動されます。これは一覧に表示されるため、そのファイルを復元すれば復元を取り消せます。そのうえで、バックアップが現在のデータベースの位置に置かれます。古いバージョンのMarginaliaで作成されたバックアップは、自動的にアップグレードされます。

入れ替えの前に、バックアップは再度検査されます（*バックアップをアップロード*と同じ検査です。*再起動時に復元*も、これに失敗したバックアップは拒否します）。検査に失敗した場合、またはアップグレードに失敗した場合、Marginaliaは現在のデータベースを保持（または元に戻す）し、通常どおり起動します。拒否されたファイルは`db-backups/rejected-restore-<time>-marginalia.sqlite`に移動され、ログに理由が記録されます。

バックアップ以降に作成された作品、パート、設定など、その後のすべてが失われます。アカウントが変更された場合、ログイン中のユーザーは再度ログインする必要があります。

<a id="copy-before-an-upgrade"></a>

## アップグレード前のコピー

新しいバージョンのMarginaliaが既存のデータベースの構造を変更する場合、まず`db-backups/pre-migration-<time>-V<version>-marginalia.sqlite`としてコピーを保存します。`<version>`はデータベースが当時のバージョンです。このコピーはバックアップの一覧に含まれるため、古いバージョンのMarginaliaをインストールし、そのコピーを[復元](#restoring)すればアップグレードを取り消せます。直近3つのコピーが保持されます。新規インストールではコピーするものがありません。コピーを作成できなかった場合（たとえばディスクが満杯の場合）は、その旨がログに記録され、アップグレードは続行されます。

途中で失敗した移行は自動的にロールバックされ、Marginaliaは起動しません。このコピーは、完了はしたものの望ましくない結果になったアップグレードのためのものです。

<a id="moving-to-another-computer"></a>

## 別のコンピューターへの移行

1. バックアップを作成し、**ダウンロード**します。
2. 新しいコンピューターにMarginaliaをインストールし、最初の起動時に一時的な管理者を作成します。
3. **バックアップをアップロード**し、**再起動時に復元**をクリックして、再起動します。
4. バックアップ内のアカウントでログインします。

古い[データフォルダー](index.md#the-data-folder)から、`data`フォルダー（作品のバックアップとパートの画像）と`extensions`フォルダーも必ずコピーしてください。または、Marginaliaを停止して`.marginalia`フォルダー全体をコピーするだけでも構いません。
