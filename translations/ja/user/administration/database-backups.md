# データベースのバックアップ

データベースのバックアップは、Marginaliaのデータベース全体の完全なコピーです。すべてのユーザーとそのすべての作品、ロアブック、設定、拡張機能のデータが含まれます。インストール環境を操作ミスや障害から守るため、また別のコンピュータへ移すために使います。単一の作品をバックアップする場合は、ユーザーは[作品のバックアップ](../books/backups.md)を使います。

![データベースのバックアップタブ](../../images/admin-database-backups.png)

<a id="creating-a-backup"></a>

## バックアップの作成

**データベースのバックアップ**タブで**バックアップを作成**をクリックします。コピーはMarginaliaの実行中に作成され、人が執筆している最中でも整合性が保たれます。一覧には**名前**、**作成日時**、**種類**（*手動*または*定期*）、**サイズ**が表示されます。ツールバーにはデータベースの現在のサイズが表示されます。

各バックアップには次のボタンがあります。

| ボタン | |
|---|---|
| **ダウンロード** | バックアップファイル（`.sqlite`）をダウンロードします。サーバーの外にもコピーを保管してください。 |
| **再起動時に復元** | バックアップを復元します。[下記](#restoring)を参照してください。 |
| ゴミ箱アイコン | バックアップを削除します。 |

**バックアップをアップロード**では、バックアップファイル（`.sqlite` または `.db`）を一覧に追加できます。たとえば別のインストール環境からダウンロードしたファイルを使えます。ファイルは最初に検査され、SQLiteデータベースではない、破損している、Marginaliaのデータベースではない（他のアプリケーションのデータベース）、または実行中のものより新しいMarginaliaのバージョンで作られている場合は、*The database can't be restored: ...* と理由が表示されて拒否されます。

!!!warning バックアップには秘密情報が含まれます
データベースのバックアップにはすべてが含まれます。すべてのユーザーのパスワードのハッシュとAPIキーも含まれます。APIキーは[データフォルダ](index.md#the-data-folder)内の`secret.key`ファイルで暗号化されていますが、このファイルはバックアップには含まれません。ただし、バックアップと`secret.key`の両方を持つ人は、APIキーを読み取れます。ダウンロードしたバックアップは、サーバー自体と同じくらい厳重に保管してください。
!!!

ファイルは[データフォルダ](index.md#the-data-folder)内の`db-backups`フォルダに保存されます。Marginalia自身が作成するコピー（[復元](#restoring)前の`pre-restore-...`と[アップグレード](#copy-before-an-upgrade)前の`pre-migration-...`）も一覧に含まれ、*手動*として表示されます。そのため、定期バックアップの世代管理によって削除されることはありません。作品のバックアップと拡張機能のJARは別ファイルであり、データベースのバックアップには含まれません。

**アップロードされたファイル（[パートの画像](../books/story-editor.md#images)）も、データベースのバックアップには含まれません**。データベースはそれらを[Resources](../resources.md)タブのエントリとしてのみ認識しており、ファイル自体はデータフォルダ内の`data/<login>/images`フォルダにあります。これで問題ありません。復元後も、エントリはバックアップ時点のものになり、それらが使用している画像もフォルダに残っています。バックアップ後に追加された画像のファイルは残存し（どこからも参照されません）、ディスク容量を使います。画像を安全に保つには、データフォルダ全体を自分のバックアップに含めるか、[作品のバックアップ](../books/backups.md#pictures-in-a-backup)にまとめてください。

**別のインストール環境**でバックアップを復元する場合は、元のインストール環境からも`secret.key`をコピーしてください（Marginaliaを停止した状態で行います）。そうしないと、保存されたAPIキーを復号できず、すべてのユーザーが再度入力する必要があります。

<a id="scheduled-backups"></a>

## 定期バックアップ

**定期バックアップ**セクションでは、バックアップを自動的に作成します。

| フィールド | |
|---|---|
| **バックアップを自動作成する** | 定期バックアップをオンにします。 |
| **スケジュール（cron）** | バックアップを作成するタイミングを設定します。[下記](#schedule-syntax)を参照してください。フィールドの下に次の3回の時刻が表示されます。 |
| **定期バックアップの保持数** | 保持する定期バックアップの数を設定します。古いものは削除されます。`0` はすべて保持します。手動およびアップロードしたバックアップは決して削除されません。 |

**スケジュールを保存**をクリックして適用します。ステータス行には、前回の定期バックアップが作成された時刻と、次回の予定時刻が表示されます。

予定時刻にMarginaliaが実行されていなかった場合（執筆中のみ実行されるデスクトップアプリでは一般的です）、次回の起動から約30秒後に、欠けていたバックアップを作成します。

<a id="schedule-syntax"></a>

### スケジュールの書式

スケジュールは5つのフィールドからなるcron式です（`minute hour day-of-month month day-of-week`）。

| 式 | 実行タイミング |
|---|---|
| `0 3 * * *` | 毎日3:00 |
| `0 */6 * * *` | 6時間ごと |
| `30 2 * * 1` | 毎週月曜日の2:30（曜日：`0` または `7` は日曜、`1` は月曜…） |
| `0 12 1 * *` | 毎月1日の正午 |
| `@daily`、`@weekly`、`@monthly` | 毎日／毎週／毎月、深夜0時に1回（`@hourly`、`@yearly`も使えます） |

時刻はサーバーのタイムゾーンで解釈されます（Dockerでは環境変数`TZ`で設定します）。

!!!
定期バックアップをオフにするには、*バックアップを自動作成する*のチェックを外し、*スケジュールを保存*をクリックします。式は保持されるため、後で再びオンにできます。式は引き続き検証されます（無効な式は決して保存されません）が、バックアップがオフの間はフィールドを空にしてもかまいません。
!!!

<a id="restoring"></a>

## 復元

Marginaliaがデータベースを使用している間は置き換えられないため、復元は**次回の起動時**に行われます。

1. バックアップの横にある**再起動時に復元**をクリックし、確認します。タブには *Database restore is scheduled. Restart the application to apply it.* と表示されます。**復元を取り消す**をクリックすると取り消せます。
2. Marginaliaを再起動します。[デスクトップアプリ](../getting-started/desktop-app.md)を終了して起動するか、[サーバー](../getting-started/docker-server.md)で`docker compose restart`を実行します。

起動時に、現在のデータベースは`db-backups/pre-restore-<time>-marginalia.sqlite`に移動されます。これは一覧に表示されるため、そのファイルを復元すれば復元を取り消せます。その後、バックアップがそこに置かれます。古いバージョンのMarginaliaで作成されたバックアップは自動的にアップグレードされます。

バックアップは組み込まれる前に再度検査されます（*バックアップをアップロード*と同じ検査で、*再起動時に復元*も検査に失敗したバックアップを拒否します）。検査に失敗した場合、またはアップグレードに失敗した場合、Marginaliaは現在のデータベースを維持（または元に戻）し、通常どおり起動します。拒否されたファイルは`db-backups/rejected-restore-<time>-marginalia.sqlite`に移動され、ログに理由が記録されます。

バックアップ以降のものはすべて失われます。すなわち、その後に作成された作品、パート、設定です。ログイン中のユーザーは、アカウントが変更されていた場合、再度ログインする必要があります。

<a id="copy-before-an-upgrade"></a>

## アップグレード前のコピー

新しいバージョンのMarginaliaが既存のデータベースの構造を変更する場合、まず`db-backups/pre-migration-<time>-V<version>-marginalia.sqlite`としてコピーを保存します。ここでのバージョンは、データベースがその時点にあったバージョンです。このコピーはバックアップの一覧に含まれるため、古いバージョンのMarginaliaをインストールし、そのコピーを[復元](#restoring)することでアップグレードを取り消せます。直近の3つのコピーが保持されます。新規インストールではコピーするものがありません。コピーが作成できない場合（たとえばディスクが満杯の場合）、ログにその旨が記録され、アップグレードは続行されます。

途中で失敗したマイグレーションは自動的にロールバックされ、Marginaliaは起動しません。このコピーは、正常に完了したものの望ましくない結果をもたらしたアップグレードのためのものです。

<a id="moving-to-another-computer"></a>

## 別のコンピュータへの移行

1. バックアップを作成し、**ダウンロード**します。
2. 新しいコンピュータにMarginaliaをインストールし、初回起動時に一時的な管理者を作成します。
3. **バックアップをアップロード**、**再起動時に復元**、再起動します。
4. バックアップ内のアカウントでログインします。

古い[データフォルダ](index.md#the-data-folder)から、`data`フォルダ（作品のバックアップとパートの画像）と`extensions`フォルダもコピーしてください。または、Marginaliaを停止して`.marginalia`フォルダ全体をコピーすることもできます。
